# TrustVault Private Object Storage

Last verified: 2026-10-22

## Phase 6.1 scope

Phase 6.1 establishes the server-only object-storage boundary. It does not yet
accept browser uploads or expose preview/download routes. Those workflows will
be built on this boundary in Phases 6.2 and 6.3.

Document bytes will live in a private Cloudflare R2 bucket. PostgreSQL retains
the authorization state and only an internal object key, digest, size, media
type, version number, and storage workflow state. The browser never receives R2
credentials, an object key, a bucket URL, or a reusable presigned URL.

## Architecture

`ObjectStorage` is a small provider-independent contract with four operations:

- `put` writes bytes and server-selected metadata;
- `get` returns a web stream for later server-side delivery;
- `head` checks provider metadata without downloading bytes; and
- `delete` supports compensating cleanup and is intentionally idempotent.

The production implementation uses the official AWS SDK v3 S3 client against
R2's S3-compatible endpoint. Tests use an in-memory implementation with the same
contract, so authorization and failure journeys never depend on a real cloud
account.

R2 objects use generated keys shaped like:

```text
documents/12/123e4567-e89b-42d3-a456-426614174000
```

The UUID is generated by the server. Document IDs, owner IDs, email addresses,
and original filenames are deliberately absent. Key parsing rejects traversal,
duplicate separators, spaces, non-allowlisted characters, and values longer than
the database column.

## Runtime configuration

```dotenv
R2_ACCOUNT_ID=32-character-cloudflare-account-id
R2_ACCESS_KEY_ID=32-character-bucket-scoped-access-key-id
R2_SECRET_ACCESS_KEY=64-character-bucket-scoped-secret
R2_BUCKET_NAME=trustvault-documents
R2_JURISDICTION=default
```

`R2_JURISDICTION` accepts `default`, `eu`, `fedramp`, or `us`. TrustVault derives
the HTTPS endpoint from the validated account ID and jurisdiction instead of
accepting an arbitrary endpoint URL.

Use a Cloudflare R2 **Object Read & Write** token restricted to this one bucket.
Do not use an account-wide administrative token. Keep the bucket private and do
not enable an `r2.dev` public URL or custom public domain.

The storage client is lazy. Missing credentials fail when a storage operation is
first requested, while static builds remain independent from production secrets.

## Security properties

- The SDK never sets a public ACL.
- Stored objects receive `Cache-Control: private, no-store` metadata.
- The server records a lowercase SHA-256 digest in object metadata; PostgreSQL
  remains the authoritative digest for later download verification.
- Empty objects, missing/invalid digests, unsafe keys, invalid bucket names, and
  placeholder credentials fail closed.
- Provider exceptions become stable storage errors so later HTTP handlers do not
  expose Cloudflare internals or credentials.
- No list-bucket operation exists in the application storage contract.

## Phase 6.1 verification

Automated tests cover key generation and rejection, configuration and endpoint
derivation, put/get/head/delete command construction, safe provider-error
translation, web-stream retrieval, defensive byte copying, idempotent deletion,
and invalid-object refusal.

This phase does not claim a live R2 connection because no project credentials
were supplied. Live bucket verification belongs to the environment/deployment
step and must confirm that public access is disabled and the token is scoped to
only `trustvault-documents`.
